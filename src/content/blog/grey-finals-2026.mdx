We define a new method on the `PyDictObject{:c}`, which simply decrements
`ma_keys->dk_log2_index_bytes{:c}` by one, and then shifts the `dk_entries{:c}` array to
the position it should be in after the decrement. Let's explore how the
`PyDictObject{:c}` and `PyDictKeysObject{:c}` are represented in cpython.

# Exploring the structs

The `PyDictObject{:c}` has the following fields:

```c
typedef struct {
    PyObject_HEAD

    /* Number of items in the dictionary */
    Py_ssize_t ma_used;

    /* Dictionary version: globally unique, value change each time
       the dictionary is modified */
#ifdef Py_BUILD_CORE
    uint64_t ma_version_tag;
#else
    Py_DEPRECATED(3.12) uint64_t ma_version_tag;
#endif

    PyDictKeysObject *ma_keys;

    /* If ma_values is NULL, the table is "combined": keys and values
       are stored in ma_keys.

       If ma_values is not NULL, the table is split:
       keys are stored in ma_keys and values are stored in ma_values */
    PyDictValues *ma_values;
} PyDictObject;
```

And `ma_keys{:c}` is a `PyDictKeysObject{:c}`, which has the following structure:

```c
/* See dictobject.c for actual layout of DictKeysObject */
struct _dictkeysobject {
    Py_ssize_t dk_refcnt;

    /* Size of the hash table (dk_indices). It must be a power of 2. */
    uint8_t dk_log2_size;

    /* Size of the hash table (dk_indices) by bytes. */
    uint8_t dk_log2_index_bytes;

    /* Kind of keys */
    uint8_t dk_kind;

    /* Version number -- Reset to 0 by any modification to keys */
    uint32_t dk_version;

    /* Number of usable entries in dk_entries. */
    Py_ssize_t dk_usable;

    /* Number of used entries in dk_entries. */
    Py_ssize_t dk_nentries;

    /* Actual hash table of dk_size entries. It holds indices in dk_entries,
       or DKIX_EMPTY(-1) or DKIX_DUMMY(-2).

       Indices must be: 0 <= indice < USABLE_FRACTION(dk_size).

       The size in bytes of an indice depends on dk_size:

       - 1 byte if dk_size <= 0xff (char*)
       - 2 bytes if dk_size <= 0xffff (int16_t*)
       - 4 bytes if dk_size <= 0xffffffff (int32_t*)
       - 8 bytes otherwise (int64_t*)

       Dynamically sized, SIZEOF_VOID_P is minimum. */
    char dk_indices[];  /* char is required to avoid strict aliasing. */

    /* "PyDictKeyEntry or PyDictUnicodeEntry dk_entries[USABLE_FRACTION(DK_SIZE(dk))];" array follows:
       see the DK_ENTRIES() macro */
};
```

`dk_indices{:c}` consists of the hash table and the actual array of elements,
as illustrated in `Objects/dictobject.c`:

```c
/*
+---------------------+
| dk_refcnt           |
| dk_log2_size        |
| dk_log2_index_bytes |
| dk_kind             |
| dk_usable           |
| dk_nentries         |
+---------------------+
| dk_indices[]        |
|                     |
+---------------------+
| dk_entries[]        |
|                     |
+---------------------+
*/
```

Now, how does the hash table work? From the example above, we see that indices
1, 2 and 3 of the hash table correspond to the values 0, 1 and 2. We can make an
educated guess: the hash of the key is used to index the hash table, and obtain
a value that will be used to index the `dk_entries{:c}` array.

This is indeed the case, as we can see in the implementation of
`dictkeys_get_index{:c}` and `find_empty_slot{:c}`, which is used during
insertion:

```c
/* macro definitions pulled from other files */
#define DK_LOG_SIZE(dk)  _Py_RVALUE((dk)->dk_log2_size)
#define DK_SIZE(dk)      (1<<DK_LOG_SIZE(dk))
#define DK_MASK(dk) (DK_SIZE(dk)-1)

/* lookup indices.  returns DKIX_EMPTY, DKIX_DUMMY, or ix >=0 */
static inline Py_ssize_t
dictkeys_get_index(const PyDictKeysObject *keys, Py_ssize_t i)
{
    int log2size = DK_LOG_SIZE(keys);
    Py_ssize_t ix;

    if (log2size < 8) {
        const int8_t *indices = (const int8_t*)(keys->dk_indices);
        ix = indices[i];
    }
    else if (log2size < 16) {
        const int16_t *indices = (const int16_t*)(keys->dk_indices);
        ix = indices[i];
    }
#if SIZEOF_VOID_P > 4
    else if (log2size >= 32) {
        const int64_t *indices = (const int64_t*)(keys->dk_indices);
        ix = indices[i];
    }
#endif
    else {
        const int32_t *indices = (const int32_t*)(keys->dk_indices);
        ix = indices[i];
    }
    assert(ix >= DKIX_DUMMY);
    return ix;
}

/* Internal function to find slot for an item from its hash
   when it is known that the key is not present in the dict.

   The dict must be combined. */
static Py_ssize_t
find_empty_slot(PyDictKeysObject *keys, Py_hash_t hash)
{
    assert(keys != NULL);

    const size_t mask = DK_MASK(keys);
    size_t i = hash & mask;
    Py_ssize_t ix = dictkeys_get_index(keys, i);
    for (size_t perturb = hash; ix >= 0;) {
        perturb >>= PERTURB_SHIFT;
        i = (i*5 + perturb + 1) & mask;
        ix = dictkeys_get_index(keys, i);
    }
    return i;
}
```

The `DK_MASK{:c}` macro is used to ensure that the computed hash that will be
used to index the hash table is capped to the size of the hash table. So, if we
were inserting a key 0x9 into our dictionary, the computed index would be at
index 1 of the hash table. Let's demonstrate this with a dictionary like such:

Notice also the `PERTURB_SHIFT{:c}` operation in `find_empty_slot{:c}`. This
operation is necessary because of the very high likelihood for collisions when
inserting into the hash table (for a hash table of size 8, we literally only
have 8 possible slots to place a key into). The way the perturbation is
calculated is quite interesting - see the comments below, from
`Objects/dictobject.c`:

```c
/*
The first half of collision resolution is to visit table indices via this
recurrence:

    j = ((5*j) + 1) mod 2**i

For any initial j in range(2**i), repeating that 2**i times generates each
int in range(2**i) exactly once (see any text on random-number generation for
proof).  By itself, this doesn't help much:  like linear probing (setting
j += 1, or j -= 1, on each loop trip), it scans the table entries in a fixed
order.  This would be bad, except that's not the only thing we do, and it's
actually *good* in the common cases where hash keys are consecutive.  In an
example that's really too small to make this entirely clear, for a table of
size 2**3 the order of indices is:

    0 -> 1 -> 6 -> 7 -> 4 -> 5 -> 2 -> 3 -> 0 [and here it's repeating]

If two things come in at index 5, the first place we look after is index 2,
not 6, so if another comes in at index 6 the collision at 5 didn't hurt it.
Linear probing is deadly in this case because there the fixed probe order
is the *same* as the order consecutive keys are likely to arrive.  But it's
extremely unlikely hash codes will follow a 5*j+1 recurrence by accident,
and certain that consecutive hash codes do not.

The other half of the strategy is to get the other bits of the hash code
into play.  This is done by initializing a (unsigned) vrbl "perturb" to the
full hash code, and changing the recurrence to:

    perturb >>= PERTURB_SHIFT;
    j = (5*j) + 1 + perturb;
    use j % 2**i as the next table index;

Now the probe sequence depends (eventually) on every bit in the hash code,
and the pseudo-scrambling property of recurring on 5*j+1 is more valuable,
because it quickly magnifies small differences in the bits that didn't affect
the initial index.  Note that because perturb is unsigned, if the recurrence
is executed often enough perturb eventually becomes and remains 0.  At that
point (very rarely reached) the recurrence is on (just) 5*j+1 again, and
that's certain to find an empty slot eventually (since it generates every int
in range(2**i), and we make sure there's always at least one empty slot).
*/
```

So using this perturbation algorithm, a given hash is guaranteed to visit every
index in the hash table exactly once before looping. During lookup, every time
the index lands on an occupied slot, we will compare the actual hash of the
`PyDictKeyEntry{:c}` to verify whether we've actually found the correct index or
if it's just a collision. When we land on an empty slot (`DKIX_EMPTY{:c}` aka
0xff), we terminate the lookup and return KeyError as there are no further
keys down the perturbation chain.

There's a small problem here: what if one of the keys in the middle of the
perturbation chain was deleted? We cannot terminate the lookup in that case, as
the keys further down the chain would then be unreachable. To differentiate a
slot that was never occupied before from a slot that was previously occupied, we
have another marker value, `DKIX_DUMMY{:c}` aka 0xfe. So, when a key is deleted,
instead of changing the index in the hash table to 0xff, we change it to 0xfe,
which indicates to the lookup that there once was a key here, and there could be
further keys down the chain, so we should not terminate the lookup.

Another caveat for lookup: if every entry in the hash table is occupied, a
lookup for a non-existent key will never terminate, since the termination
condition is when it lands on `DKIX_EMPTY{:c}`. To prevent this, the hash table
can never be allowed to fill up completely, ie. `dk_usable + dk_nentries{:c}`
must be smaller than the actual capacity of the dictionary. This is defined in
the `USABLE_FRACTION{:c}` macro:

```c
/* USABLE_FRACTION is the maximum dictionary load.
 * Increasing this ratio makes dictionaries more dense resulting in more
 * collisions.  Decreasing it improves sparseness at the expense of spreading
 * indices over more cache lines and at the cost of total memory consumed.
 *
 * USABLE_FRACTION must obey the following:
 *     (0 < USABLE_FRACTION(n) < n) for all n >= 2
 *
 * USABLE_FRACTION should be quick to calculate.
 * Fractions around 1/2 to 2/3 seem to work well in practice.
 */
#define USABLE_FRACTION(n) (((n) << 1)/3)
```

During insertion, every time the index lands on a currently occupied slot, the
perturbation will be applied, and we will continue searching down the chain
until we find an empty slot, either `DKIX_EMPTY{:c}` or `DKIX_DUMMY{:c}`.

Now that we mostly understand how a dictionary works in CPython, let's look at
our primitive again.

# Exploiting the hash table

Our primitive decrements `dk_log2_index_bytes` by 1, and copies the old
`dk_entries{:c}` array to the new position it should be in. The implementation
of `DK_ENTRIES{:c}` is below:

```c
static inline void* _DK_ENTRIES(PyDictKeysObject *dk) {
    int8_t *indices = (int8_t*)(dk->dk_indices);
    size_t index = (size_t)1 << dk->dk_log2_index_bytes;
    return (&indices[index]);
}
static inline PyDictKeyEntry* DK_ENTRIES(PyDictKeysObject *dk) {
    assert(dk->dk_kind == DICT_KEYS_GENERAL);
    return (PyDictKeyEntry*)_DK_ENTRIES(dk);
}
```

Now, during lookup, the hash of the first element in the `dk_entries{:c}` array
will overlap with the last 8 slots in the `dk_indices{:c}` hash table. This
means that we can use the first element's hash to control some indices of the
hash table! Obviously, we can use this to index a fake `PyDictKeyEntry{:c}`
that is placed after the entries array. Let's get to faking stuff!

# fakeobj galore

We'll use the `bytes` object to place our fakeobjs in memory. Note that pymalloc
is a pool-based allocator, but not all same-sized objects will be placed in the
same pool as there can be multiple pools handling objects of the same size.
Therefore, we should try our best to allocate our target objects in the same
pool by keeping their sizes the same, but if it fails we can simply spray more
same-sized objects until our desired pool is used.


First off, let's make a fake `PyDictKeyEntry{:c}` that points to a fake
bytearray. This fake bytearray will be accessible via `victim_dict[0x8]{:py}`,
and we'll use it as our arbitrary write primitive. 0x8 is the first index in the
portion of the hash table that we control; the hash value that overwrites the
hash table should therefore be 0x00000000000000XX, where XX is
(offset_to_fakeobj / 0x18). Empirically, this value is 0x24.

Finally, we are ready to create the fakeobj that will give us RCE. We will
target the vtable inside a fake type, and set the reprfunc field to system.
Then, we will use a fake object to reference this fake type, and on calling
`repr(fakeobj){:py}` we should get our shell. Since the object itself is the
first parameter passed to reprfunc, we must put the /bin/sh string in the
refcount of the object (but because refcount is volatile we need to check in gdb
how much to decrement it by). Lastly, we will put this fakeobj in the list we
created earlier, using our write primitive.

```py

faker_stuff += pack(id(type))
faker_stuff += b"a"*0x48
faker_stuff += pack(system)
```
